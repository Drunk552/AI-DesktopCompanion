# AI 桌面宠物工程按优先级排序的整改清单

## 1. 文档目的

本文基于以下文档与当前工程实现的对照检查结果，整理出一份按优先级排序的整改清单：

- `AI 桌面宠物 Brain 层设计文档.md`
- `AI 桌面宠物第二阶段 Brain 落地实施方案.md`
- `AI 桌面宠物第一阶段目录迁移实施方案.md`
- `AI 桌面宠物框架优化方案.md`
- `AI 桌面宠物五层架构目录重组设计文档.md`

本文重点不是重复架构设计，而是明确：

1. 当前工程还没有达到文档要求的部分
2. 哪些问题必须优先整改
3. 哪些问题可以延后处理
4. 哪些问题属于长期工程优化项

---

## 2. 当前整体判断

当前工程已经完成了大量结构性工作，主要包括：

- `app/`、`perception/`、`shared/` 目录已落地
- `brain/` 目录已建立并投入使用
- `controller/session.*` 已迁入 `brain/session.*`
- `brain/brain_controller.*` 已引入
- `app/app_event_bus.*` 已从 UI 侧上移出来
- `conversation_orchestrator`、`emotion_state`、`relation_state` 已初步拆出
- `action/` 与 `intelligence/` 目录已经开始形成

因此，当前工程并不是“还没开始重构”，而是：

**已经完成第一阶段和第二阶段的大部分工作，但在 Brain 编排收口、Application 瘦身、事件语义统一、长期目录命名与构建治理上还没有完全达到文档目标。**

---

## 3. 必须先做

这一部分属于当前最影响架构目标达成的项。若不先处理，这个工程虽然能继续跑，但会继续停留在“部分 Brain 化”，而不是“Brain 真正接管系统编排”。

### 3.1 让 Brain 成为所有模式下的唯一编排入口

当前问题：

- UI 模式主要通过 `BrainController` 处理输入与感知
- 但 `runChatMode()` 和 `runFullMode()` 里仍直接调用 `session_.orchestrator().handleTurn(...)`
- 这意味着部分模式仍绕过 Brain，导致 Brain 不是唯一系统级决策入口

对应文档要求：

- Brain 是唯一系统级思考者
- BrainController 应接管系统编排权
- Application 不应继续承担主要会话决策逻辑

建议整改：

1. 将 chat/full 模式下的对话入口改为通过 `BrainController`
2. 不再让 `Application` 直接调 `Session::orchestrator()` 处理对话轮次
3. 统一由 Brain 负责：是否接受输入、是否忙碌、是否开始 turn、turn 结束后的状态更新与输出

完成标准：

- 所有模式下的对话处理都经由 Brain
- `Application` 不再直接调用会话编排主流程

### 3.2 继续瘦身 `Application`

当前问题：

- `Application` 仍同时承担模式运行、线程管理、摄像头循环、UI 驱动、部分流程控制
- 这和文档中“Application 负责程序运行，Brain 负责系统决策”的边界还不够一致

对应文档要求：

- `Application` 应逐步只保留程序入口、模块初始化、生命周期协调等职责
- 具体模式逻辑应逐步从 Application 中拆开

建议整改：

1. 先把 Brain 已接手的职责从 `Application` 中继续删掉
2. 保留 `Application` 负责：模式选择、生命周期、线程托管、退出控制
3. 不在 `Application` 中继续增加新的业务判断逻辑

完成标准：

- `Application` 不再直接做主要业务编排
- 代码语义上能看出它是运行容器，而不是业务控制器

### 3.3 补上 Brain 对系统事件的统一编排入口

当前问题：

- Brain 现在主要处理两类入口：用户文本输入、感知情绪输入
- 还没有形成文档推荐的 user/perception/system 三类事件统一接入结构
- `event_router.*` 也尚未落地

对应文档要求：

- Brain 必须能处理非对话事件
- Brain 应统一处理系统事件
- 推荐引入 `event_router`

建议整改：

1. 在 `brain/` 内补上事件路由入口，哪怕先做轻量版也可以
2. 明确区分：
   - `user.*`
   - `perception.*`
   - `system.*`
3. 为后续 idle、startup、shutdown、主动行为等事件留统一收口点

完成标准：

- Brain 不再只是“聊天入口 + 感知入口”
- 系统事件能通过统一 Brain 路径进入处理

### 3.4 把主动行为从“感知触发附属逻辑”提升为“系统级 Brain 逻辑”

当前问题：

- 现在主动行为主要是在 `handlePerceptionEmotion()` 中顺带触发
- 这会让主动行为过度依赖“识别到情绪”这个单一来源
- 文档里的目标是支持 idle timeout、关系变化、长时间未互动等非对话事件

对应文档要求：

- Brain 必须处理非对话事件
- Brain 应能判断是否主动打扰、是否安静陪伴

建议整改：

1. 增加 `system.idle.timeout` 之类的系统输入事件
2. 将主动行为决策从单纯的感知回调里抽离出来
3. 让主动行为的触发条件可由：
   - 空闲时长
   - 最近互动状态
   - 当前关系状态
   - 当前情绪状态
   共同决定

完成标准：

- 主动行为不再只依赖摄像头情绪输入
- Brain 开始具备真正的“桌宠主动性”决策能力

---

## 4. 可以后做

这一部分已经影响到架构完整性和长期维护性，但不会像前一组那样直接妨碍 Brain 成为系统中枢。建议在核心编排收口完成后尽快处理。

### 4.1 补全 `event_router.*`

当前问题：

- 文档推荐的 `event_router.*` 文件还不存在
- 当前事件分发主要还是集中在 `BrainController`

建议整改：

1. 引入 `brain/event_router.h/.cpp`
2. 让 `BrainController` 更像外部门面
3. 把事件分类、路由、入口分发逐步从 `BrainController` 中拿出去

价值：

- 避免 `brain_controller.cpp` 重新长成新的大类
- 为后续更多事件类型接入留出位置

### 4.2 继续完善 `BrainState`

当前问题：

- `BrainState` 已存在，但还不是文档里建议的完整状态快照
- 目前缺少如 `current_persona`、`recent_emotion_trend`、`active_mode` 等信息

建议整改：

1. 在不引入过度复杂度的前提下补充关键字段
2. 明确哪些字段是“Brain 内部状态”，哪些字段只是 UI 展示派生值
3. 让 `BrainState` 成为 Brain 对系统现状的统一快照

价值：

- 后续 UI、Action、策略设置页都能围绕统一状态快照工作
- 减少零散读取内部对象的情况

### 4.3 统一事件语义命名

当前问题：

- 文档推荐的事件语义是 `ui.chat.append`、`ui.status.*`、`action.pet.expression` 这类“语义事件”
- 当前工程更多是 `action.chat.reply`、`action.pet.emotion`、`action.notification.show` 这类偏执行侧命名

建议整改：

1. 梳理当前系统事件命名表
2. 统一区分：
   - Brain 输入事件
   - Brain 输出事件
   - Action 执行事件
   - UI 展示事件
3. 若不想一次性重命名，也至少先建立集中定义文件并冻结新命名规则

价值：

- 事件流更容易读懂
- 更符合“Brain 输出语义，UI/Action 负责执行”的设计原则

### 4.4 收敛 UI 页面切换接口，减少字符串路由

当前问题：

- `UiController` 仍使用 `switchScreen(const std::string& screenId)`
- 内部通过字符串 `if/else` 做页面切换

对应文档要求：

- 页面切换应尽量统一成枚举或路由对象

建议整改：

1. 对外暴露更稳定的 `ScreenType` 或等价路由类型
2. 字符串仅保留在极少数边界转换位置
3. 避免后续事件或业务代码继续传播裸字符串 screen id

价值：

- 降低拼写错误和重构风险
- 让 UI 路由边界更清晰

### 4.5 继续收口 UI 与业务边界

当前问题：

- 系统总线已从 UI 中上移，这是好事
- 但 UI 仍然订阅并处理很多跨域事件，且部分接口仍然保留比较宽泛的操作能力

建议整改：

1. 继续坚持 UI 只做展示和输入采集
2. 不在 UI 层新增业务推理、状态判定、跨层协调逻辑
3. 新增功能时优先判断是否应进 Brain/Action，而不是直接塞进 UI Controller

价值：

- 避免 UI 再次回流成“半业务层”

## 5. 纯优化项

这一部分更多是长期工程质量、命名一致性、构建治理与目录收敛问题。短期不做不会破坏架构主线，但长期值得逐步完成。

### 5.1 将 `intelligence/memory/sqlite.*` 重命名为更稳定的领域命名

当前问题：

- 目录已经迁到了 `intelligence/memory/`
- 但文件名仍然是 `sqlite.*`
- 文档建议用 `memory_db.*` 这类领域语义名，而不是实现技术名

建议整改：

1. 将文件名从 `sqlite.*` 逐步调整为 `memory_db.*`
2. 保持类名与文件名语义一致

价值：

- 避免以后换存储实现时目录和文件名失真

### 5.2 继续整理 `CMakeLists.txt`

当前问题：

- 仍使用全局 `include_directories(...)`
- 源文件仍是一个大 `SOURCES` 列表

对应文档建议：

- 使用 `target_include_directories`
- 按层组织源文件列表

建议整改：

1. 逐步替换全局 include 方式
2. 将源文件列表按 `APP`、`BRAIN`、`INTELLIGENCE`、`ACTION`、`UI`、`SHARED` 分组
3. 保持改动小步推进，不和业务重构混在同一次提交里

价值：

- 构建脚本本身能反映架构边界
- 后续拆分 target 或做模块治理会更容易

### 5.3 补齐长期目标中的 `mode_runner_*` 结构

当前问题：

- 文档长期目标里建议引入 `mode_runner_ui.*`、`mode_runner_chat.*` 等
- 当前尚未落地

建议整改：

1. 在 Brain 编排主线稳定后，再考虑将各模式运行细节从 `Application` 进一步抽出
2. 优先抽那些已经比较独立的模式循环

价值：

- 让 `Application` 最终退化成真正的入口协调器
- 后续新增模式或测试模式更方便

### 5.4 继续细化 Brain 内部职责

当前问题：

- 已经拆出 `conversation_orchestrator`、`emotion_state`、`relation_state`
- 但后续随着事件变多，`BrainController` 与策略逻辑仍可能继续膨胀

建议整改：

1. 观察后续新增逻辑是否开始挤进 `BrainController`
2. 若明显膨胀，再进一步拆分状态同步、策略判断、主动行为策略等内部模块
3. 保持“先有真实痛点，再做拆分”原则

价值：

- 避免为了架构名词而过度设计
- 也避免 Brain 重新变成新的超大类

### 5.5 进一步统一文档与实际目录命名

当前问题：

- 工程总体方向已经和文档趋同
- 但文档里的部分命名和当前代码仍存在轻微差异，例如事件名、文件名、某些类职责边界

建议整改：

1. 当关键重构完成后，反向更新文档
2. 明确哪些是“最终目标命名”，哪些是“过渡态命名”
3. 避免后续设计文档继续混用多套名字

价值：

- 降低维护者理解成本
- 文档可以真正成为工程演进依据，而不是历史记录

---

## 6. 推荐整改顺序

建议按下面顺序推进，而不是并行大改：

1. 先让所有模式的对话编排都收口到 Brain
2. 再把 `Application` 中剩余的业务编排逻辑继续剥离
3. 再补 system 事件入口与主动行为统一编排
4. 然后补 `event_router` 与更完整的 `BrainState`
5. 最后再做 UI 路由收敛、命名治理、CMake 整理、文件重命名等优化项

这个顺序的核心原因是：

**先收编排权，再做结构美化。**

如果顺序反过来，容易出现目录更漂亮了，但系统真实决策链路仍然分散在 `Application`、`UI`、`Brain` 多处的问题。

---

## 7. 一句话结论

当前工程最优先的整改目标不是继续改目录，而是：

**把系统编排权彻底收口到 Brain，让 `Application` 退回运行容器角色，再逐步补齐系统事件、主动行为和事件语义的一致性。**
